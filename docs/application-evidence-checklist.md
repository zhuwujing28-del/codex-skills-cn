# OSS 申请证据复核清单

这份清单用于提交 Codex for Open Source 申请前的最后一次证据复核。它把“项目做了什么”和“申请材料能够证明什么”分开，避免把仓库内的自测结果写成外部采用或社区影响力。

## 复核顺序

1. **先确认范围**：写清楚项目服务的维护者、覆盖的工作流，以及当前仍处于早期阶段的部分。
2. **再确认实现**：从 [`README.md`](../README.md)、`skills/` 和示例索引中挑选最少但有代表性的材料。
3. **再确认验证**：运行 `python scripts/validate-skills.py`，记录本地命令、结果和运行日期；同时单独标注 CI 是否已通过。
4. **最后确认反馈**：只引用公开 issue、PR 或经过脱敏的 maintainer workflow report，并保留原始链接或文件路径。

## 证据表

| 申请主张 | 最小证据 | 表述边界 |
| --- | --- | --- |
| 有可复用的中文 skills | 一个具体 `skills/<name>/SKILL.md` 与对应 README | 不写成广泛用户采用 |
| 覆盖真实维护工作流 | 一个维护者示例，包含输入、证据、验证和下一步 | 不把示例当成真实外部案例 |
| 仓库可维护 | `python scripts/validate-skills.py` 输出与 CI 链接 | 本地通过不等于所有平台均通过 |
| 正在根据反馈改进 | 公开 issue、PR 或脱敏 usage report 加对应 changelog 条目 | 单条反馈只证明一个改进信号 |
| 适合继续投入 | 明确的当前缺口、下一步和所需资源 | 不承诺尚未测量的影响指标 |

## 提交前检查

- [ ] 每个数字都能在仓库文件、公开 GitHub 页面或带日期的报告中复核。
- [ ] 每个“用户”“采用”“影响”类表述都说明了证据来源和样本范围。
- [ ] 示例、日志和报告已去除 token、私有 URL、个人信息及未公开项目细节。
- [ ] 申请材料中的 skill 数量、eval 数量和链接与当前 `main` 一致。
- [ ] 已区分本地验证、GitHub Actions 验证，以及 push/发布状态。
- [ ] 若本轮没有新证据，保留诚实的限制说明，而不是补写推测性成果。

## 维护规则

申请材料发生结构性变化时同步更新本清单；单次维护只需补充能被当前仓库证据支持的条目。外部反馈应先进入 issue 或脱敏报告，再决定是否更新申请叙述。
